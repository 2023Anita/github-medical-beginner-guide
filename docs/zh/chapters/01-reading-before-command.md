## 1. 学 GitHub 的正确顺序：先会看项目，再学写命令

新手最常见的误区，是一上来就学 Git 命令。

比如：

- `git clone`
- `git commit`
- `git push`
- `git branch`
- `git merge`

这些当然重要，但不是第一步。

对医护人员来说，第一阶段更应该学的是：

| 学习层级 | 你真正要解决的问题 | 医疗场景里的类比 |
|---|---|---|
| 第 1 层：看懂 | GitHub 页面上每个区域是什么意思 | 先看懂一份病历结构 |
| 第 2 层：判断 | 这个项目能不能信、能不能用 | 判断一篇论文质量或指南等级 |
| 第 3 层：下载 | 我该下载 Release 还是源码 | 区分“临床可用药品”和“实验室原料” |
| 第 4 层：复用 | 我能不能让 AI 帮我改成自己的工具 | 基于已有临床路径做本院适配 |
| 第 5 层：发布 | 我怎样把自己的项目放上去 | 把 SOP、数据字典、研究代码规范归档 |
| 第 6 层：协作 | 如何提 Issue、Fork、PR | 像病例讨论、质控反馈、指南修订 |

所以这篇指南不从命令开始，而从“怎么看懂一个项目”开始。

## 2. GitHub 到底是什么？用医院系统来理解

一句话：

> **GitHub 是全球最大的开源项目平台。对医护人员来说，它像一个公开的医学工具库、科研代码库、项目说明书库和协作平台。**

你可以把 GitHub 理解成 4 个东西。

### 2.1 它像“公开的科研项目档案室”

一个 GitHub 仓库通常会包含：

- 项目说明；
- 代码；
- 数据处理流程；
- 示例文件；
- 安装方法；
- 使用说明；
- 更新记录；
- 问题反馈；
- 贡献者列表。

这有点像一个科研项目的完整归档：

- 研究方案；
- 数据字典；
- 统计分析计划；
- R / Python 脚本；
- 图表生成代码；
- 结果复现说明；
- 修改记录。

如果一个医学研究只给你结论，不给方法，你会谨慎。  
同样，如果一个 GitHub 项目只有代码，没有说明，也要谨慎。

### 2.2 它像“医疗工具说明书集合”

很多 GitHub 项目不是给你看的代码，而是给你用的工具。

比如：

- DICOM 图像查看或处理工具；
- CT / MRI 分割模型；
- 文献爬取和整理脚本；
- PubMed 检索增强工具；
- 医学文本标注工具；
- 临床数据脱敏工具；
- R 语言统计模板；
- 科研绘图脚本；
- 医疗 AI demo。

你不一定要看懂每一行代码，但你要能看懂：

1. 它做什么；
2. 适合谁；
3. 有没有风险；
4. 怎么安装；
5. 怎么运行；
6. 是否还能维护；
7. 是否适合真实临床或只适合研究演示。

### 2.3 它像“临床质控和协作平台”

开源项目不是作者写完就结束。

别人可以：

- 在 Issue 里反馈 Bug；
- 提出功能建议；
- 补充文档；
- 修复错误；
- 贡献代码；
- 讨论使用场景。

这很像医院里的质控闭环：

| 医疗场景 | GitHub 对应物 |
|---|---|
| 发现医嘱流程有问题 | 提 Issue |
| 补充护理路径说明 | 改 README 或文档 |
| 提交一版修订 SOP | Pull Request |
| 主任 / 质控组审核 | Maintainer review |
| 新版制度发布 | Release |
| 留下修改记录 | Commit history |

### 2.4 它像“AI 时代的积木仓库”

AI 写代码就像一个很快的助手。

但如果没有现成积木，它会从零开始猜。  
如果你先找到一个靠谱开源项目，它就可以在已有基础上帮你改。

举例：你想做一个“围术期麻醉风险提示小工具”。

从零开始，你可能不知道：

- 前端页面怎么做；
- 表单怎么设计；
- 风险规则怎么写；
- 报告怎么导出；
- 数据怎么存；
- 如何部署。

但你可以先在 GitHub 找：

- `clinical decision support app`
- `medical risk calculator`
- `perioperative risk calculator`
- `streamlit medical app`
- `fastapi healthcare demo`

然后让 AI 帮你理解项目，再改成自己的教学 demo。
